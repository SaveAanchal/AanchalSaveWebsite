Problem

Solve inverse kinematics for a 7-DOF robotic manipulator faster and more generally than traditional Jacobian-based or optimization-based solvers, which are slow, susceptible to singularities, and require per-configuration tuning.

Why It Is Hard

A 7-DOF arm is kinematically redundant — infinitely many joint configurations map to the same end-effector pose. Closed-form IK is intractable; iterative solvers diverge near singularities or get trapped in local minima. A learned approach must generalize across the full reachable workspace from finite simulation data.

System Overview

A PyTorch network trained on (end-effector pose) → (joint angles) mappings generated in Gazebo + Simulink. A forward kinematics model serves as a validation layer before any solution is actuated, closing the correctness loop.

Architecture & Pipeline

Pose Target → IK Neural Net → Candidate θ → FK Validation → Actuate

Technical Approach

  • Generated large-scale simulation dataset from Gazebo + Simulink covering the full joint workspace
  • Trained a multi-layer feedforward network (PyTorch) with custom loss weighting joint angle accuracy and workspace coverage
  • Introduced a FK validation loop: candidate joint angles are verified by passing through a forward kinematics model before deployment, rejecting invalid solutions
  • Integrated with ROS2 for real-time deployment on the manipulator

Design Decisions

  • Chose a neural approach over optimization-based IK to avoid singularity issues and enable sub-millisecond inference
  • FK validation loop was added after observing that raw network outputs occasionally violated joint limits near workspace boundaries
  • Simulation data generation in Gazebo enabled diverse pose sampling without physical robot wear

Results

  • Solution accepted for oral presentation and publication at IEEE ICMRE 2026 (IEEE Xplore)
  • Novel architecture filed toward NASA New Technology Report (patent process)
  • Demonstrated generalization across the full reachable workspace of the 7-DOF arm with FK validation rejection rate below 5% on the test set

Failures & Improvements

  • Early models failed near singular configurations; resolved by adding targeted training data near those regions
  • Future work: extend to dynamic configurations and integrate with a motion planner for full manipulation pipelines

Problem

Enable a physical rover to navigate autonomously through unstructured outdoor terrain by determining in real time which areas are safe to traverse — without relying on GPS or pre-built maps.

Why It Is Hard

Raw LIDAR point clouds encode geometry but not traversability. The pipeline must extract meaningful terrain features (slope, roughness, height discontinuities) fast enough to feed a planner in real time, and the cost function must be tuned so conservative enough to avoid tipping without being so restrictive the rover gets stuck.

System Overview

A ROS2 + C++ pipeline processes LIDAR scans into point clouds, estimates local surface normals, extracts terrain features per grid cell, evaluates a cost function, and publishes a cost map consumed by the motion planner — all in real time on the rover's onboard computer.

Architecture & Pipeline

LIDAR Scan → Surface Normals → Terrain Features → Cost Function → Planner

Technical Approach

  • Used PCL (Point Cloud Library) in C++ for efficient surface normal estimation from 3D point clouds
  • Discretized the terrain into a 2D grid; computed slope angle, roughness (normal variance), and height discontinuities per cell
  • Designed a cost function that maps feature vectors to scalar traversability scores, with separate weights per feature class
  • Published the resulting cost map on a ROS2 topic consumed by the path planner at the planning frequency

Design Decisions

  • Chose geometric feature extraction over learned traversability models to maintain interpretability and reduce compute on the onboard system
  • Grid resolution was tuned empirically to balance map resolution against update frequency constraints
  • Cost function weights were validated in simulation before hardware deployment

Results

  • Deployed on a physical competition rover with successful autonomous navigation in unstructured outdoor terrain
  • Real-time cost map updates at planning frequency; rover avoided obstacles and steep grades in testing

Failures & Improvements

  • Sparse LIDAR returns in tall grass created false high-cost regions; addressed by height-based outlier filtering
  • Future work: integrate learned traversability estimation to handle semantically difficult terrain (mud, loose gravel)

Problem

Build a full perception-to-control autonomy stack on the F1TENTH 1:10 scale car platform that detects obstacles, classifies them, and commands avoidance behaviors in real time — validating the pipeline on hardware.

Why It Is Hard

The F1TENTH platform moves fast relative to its scale, leaving little time between perception and control. The pipeline must handle variable lighting, partial occlusion, and detection latency while remaining within the computational budget of the onboard computer. End-to-end latency from camera to actuator must be low enough that the car responds before reaching the obstacle.

System Overview

A ROS2 pipeline integrates stereo camera depth estimation with YOLO-based object detection, fuses 2D detections with depth to get 3D object locations, passes object state to a decision module that selects avoidance or waypoint-following behaviors, and commands the vehicle controller.

Architecture & Pipeline

Stereo Camera → YOLO Detection → 3D Localization → Decision Logic → Control

Technical Approach

  • Ran YOLO on RGB frames for object detection; paired with stereo disparity map to estimate 3D distance to each detected object
  • Decision module evaluated object proximity, classification confidence, and relative velocity to select avoidance, slow-down, or continue behaviors
  • ROS2 node graph structured to minimize latency between perception outputs and control commands
  • Validated closed-loop on the F1TENTH platform in the Georgia Tech Active Safety Lab

Design Decisions

  • Chose YOLO for detection (not a classical CV approach) to handle diverse object classes robustly under lab lighting variation
  • Stereo depth (not LIDAR) was the platform constraint; careful stereo calibration was essential for accurate 3D localization
  • Decision logic kept deliberately simple (threshold-based) to maintain predictability on hardware before complexity was added

Results

  • Validated closed-loop perception-to-control latency under 100 ms on hardware
  • Successful obstacle detection and avoidance in lab environment across multiple test scenarios

Failures & Improvements

  • Stereo depth estimation degraded at close range due to disparity saturation; addressed with near-range fallback detection logic
  • Future work: replace threshold-based decision logic with an MPC layer for smoother, predictive avoidance trajectories

Problem

Build simulation and analysis tools for three distinct spacecraft applications: (1) constellation architecture trade studies at SpaceX, (2) CubeSat debris capture mission planning at Skyfall Space, and (3) orbit navigation software for Georgia Tech's GPDM CubeSat mission.

Why It Is Hard

High-fidelity orbital mechanics requires numerical integration of perturbed equations of motion; naive implementations accumulate significant error over time. Constellation trade studies involve a large design space where simulation throughput directly limits the quality of decisions. CubeSat missions with constrained power and propulsion make debris intercept planning a tightly constrained optimization problem.

System Overview

Orekit (Java/Python) provides the propagation core; C++ and Python layers handle simulation logic, metric computation, and visualization. Three separate applications built on a shared simulation foundation: constellation trades (SpaceX), debris intercept planning (Skyfall), and mission navigation software (GT SSDL).

Architecture & Pipeline

Initial Conditions → Orekit Propagation → Sim Logic → Analysis & Viz

Technical Approach

  • SpaceX: Built C++ + Python simulation pipeline for constellation architecture trades; integrated GNC metrics dashboards with Matplotlib, Pandas, and Bokeh for interactive design-space exploration
  • Skyfall Space: Developed debris propagation models and CubeSat intercept simulations; modeled capture probability as a function of relative state uncertainty and propulsion constraints
  • GT SSDL: Built Orekit + Python navigation software for the GPDM mission, implementing orbit propagation, thrust estimation, and mission integration workflows; contributed to cleanroom testing and post-launch ops planning

Design Decisions

  • Orekit chosen over custom propagators for high-fidelity force models (J2, drag, solar pressure) without reinventing the physics core
  • C++ used for computationally intensive simulation loops; Python used for analysis, dashboards, and rapid iteration
  • Bokeh enabled interactive dashboards for constellation trade exploration, allowing engineers to slice across design parameters without re-running simulations

Results

  • Simulation tools deployed in active mission planning workflows at SpaceX and Skyfall Space
  • GT SSDL navigation software integrated into GPDM mission pipeline with cleanroom validation completed
  • Debris propagation models supported Skyfall's NASA funding proposal and mission design review

Failures & Improvements

  • Early Orekit integration had state vector frame-of-reference bugs that produced incorrect thrust estimates; resolved through systematic unit testing against known analytic solutions
  • Future work: extend debris intercept planner with a full trajectory optimization layer using differential dynamic programming
